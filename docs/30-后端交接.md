## 二、数据结构约定（前端已按此实现，请对齐）

### 2.1 结构化消息（约局卡片）

**消息对象新增 `type: 'structured'`**，内容放在 `meta`：

```json
{
  "_id": "...",
  "type": "structured",
  "content": "",
  "meta": {
    "time": "周六 19:00",
    "place": "南湖操场",
    "note": "带水",
    "card_id": "可选，关联的搭子卡片 id",
    "venue_id": "可选，如果 place 是场地库里的场地"
  },
  "is_me": false,
  "created_at": 1730000000000
}
```

**前端兼容性**：`meta` 传 **JSON 字符串**或**对象**都能解析（`scOf()` 里做了 `typeof` 判断 + `try/catch`）。
建议数据库存 String，接口返回时保持 String 即可。

**字段说明**：

| 字段 | 必填 | 说明 |
|---|---|---|
| `time` | 是 | 展示用文案，前端不解析成时间戳。**格式化由后端做**（"周六 19:00" 比 ISO 串好读） |
| `place` | 是 | 展示用文案 |
| `note` | 否 | 补充说明，一行 |
| `card_id` | 否 | 关联搭子卡片，用于「确认」后回写状态 |
| `venue_id` | 否 | 有场地库时给，前端可跳场地详情 |

**为什么格式化放后端**：前端如果自己把 ISO 串转成「周六 19:00」，会遇到时区、跨天、相对日期（明天/下周六）三个坑。后端一次算好，前端只展示。

### 2.2 AI 情绪提示

**新增 `type: 'ai-hint'`**：

```json
{
  "_id": "...",
  "type": "ai-hint",
  "content": "看起来今天有点累？",
  "created_at": 1730000000000
}
```

- `content` 是完整的一句话，前端直接展示，**不做任何拼接或改写**
- 前端只负责渲染 + 关闭，**不做任何自动情绪识别**
- 关闭时前端目前只做本地移除，需要接口落库（见 3.3）

## 三、后端待办

### P0-1 `card-list` 补 `matched_total`

**现状**：首页需求流调 `card-list`（`scope: 'school'`, `page_size: 3`），
前端读 `data.matched_total` 来显示「N 人和你同频」胶囊和活人信号。

```json
{
  "code": 0,
  "data": {
    "list": [ ... ],
    "matched_total": 6,      // ← 需要这个
    "has_more": true,
    "total": 12
  }
}
```

**要求**：
- 类型是 `number`，**不能是字符串**（前端 `typeof === 'number'` 才采用）
- 算不出来时**返回 `null` 或不返回**，不要返回 `0` ——
  前端把 `null` 当「不知道」不显示，把 `0` 当「真的没人」显示不同文案

### P0-2 结构化消息的发送与渲染

**需要支持**：
1. `message-send` 接受 `type: 'structured'` + `meta`
2. `message-list` 返回时带上 `type` 和 `meta`

**建议新增的发送入口**（前端骨架里还没做入口，等接口定了再加）：

```
POST meetup-invite
  { conversation_id, time, place, note, card_id? }
  → 生成一条 type='structured' 的消息
```

### P0-3 约局确认

前端 `confirmStructured()` 目前是**临时方案**：发一条普通文本「好，就这个时间地点 👍」。
这样约局状态就丢了 —— 需要正式接口。

```
POST meetup-confirm
  { message_id, action: 'accept' | 'decline' }
  → { code: 0, data: { status: 'accepted' } }
```

**要解决的问题**：两个人各自点「确认」后，怎么知道双方都同意了？
建议在 `card` 或新的 `meetup` 表上维护状态机：

```
pending → one_confirmed → both_confirmed
        ↘ declined
```

前端需要拿到 `status` 来改卡片样式（已确认的卡片要变样，不能还能点）。

### P0-4 AI 提示的下发与关闭

**下发时机由后端决定**（前端不做识别）。建议规则（供参考，具体你来定）：

| 触发 | 示例文案 |
|---|---|
| 连续 N 条消息都是短句且无表情 | 「今天话不多，还好吗？」 |
| 深夜 23:00 后仍在聊 | 「这么晚还没睡？」 |
| 聊天里出现高频负面词 | 「听起来不太好受」 |

**接口**：

```
POST hint-dismiss
  { message_id }
  → { code: 0 }
```

**为什么要落库**：如果只在前端移除，用户下次进来同一条提示又出现，
会觉得「这个 App 在反复试探我」——情绪陪伴产品最忌讳这个。

**频控建议**：同一条 hint 不要重复推；同一会话 24 小时内最多 1 条。

### P1-1 同频圈「发现」tab 的真实内容

**现状**：`card-list` 的 `scope: 'all'` 能返回全站内容，但「发现」tab 现在没有独立的聚合逻辑。

**需求**：跨校聚合的动态流。如果后端短期做不了，**前端已按文档要求做了兜底**——
同校为空时自动切到「发现」，但「发现」为空时只能显示空态。

**最低要求**：`scope: 'all'` 返回的内容**不要只限同校**，否则「发现」和「同校」没区别。

## 六、一个建议

`matched_total` 这个字段值得认真做。

首页现在把「N 人和你同频」放在标题旁，把每张卡的同频度放在右上角 ——

## 八、首页重构 + 同频圈改版带来的新需求（2026-10-27 追加）

> 前七章的内容仍然有效。本章是**新增**部分，来自 10-26 晚到 10-27 凌晨的两处改版。

### 8.1 首页数字卡：需要 2 个新字段

首页顶部有一个白色胶囊数字卡，三格数字：

| 位置 | 现在怎么来的 | 需要后端做什么 |
|---|---|---|
| 同频中 | `matchTotal`（`card-list` 已返回 `matched_total`） | 已有，不用动 |
| 我的需求 | **前端数当前列表里的 `is_mine`** | 不可靠，见下 |
| 我的搭子 | **写死 0** | 需要新字段 |

**「我的需求」的问题**：现在前端用 `feed.filter(c => c.is_mine).length`。
但 `feed` 只拉了 3 条（`page_size: 3`），而且只包含"正在找搭子"的卡片。
用户发过 5 条、其中 3 条已完成，这个数字就会错。

**建议新增聚合接口**：

```
GET home-summary
→ {
    code: 0,
    data: {
      matched_total: 8,        // 此刻同频人数（可复用 matched_total 的口径）
      my_open_cards: 2,        // 我发布的、还在进行中的需求数
      my_buddy_count: 3        // 已建立的搭子关系数
    }
  }
```

**三个字段的类型要求**：

- 都是 `number`，**不能是字符串**
- 算不出来时返回 `null`，**不要返回 0**
  —— 前端对 `null` 和 `0` 显示不同文案（`null` = 不显示，`0` = 显示 0）

**为什么值得单独做一个接口**：数字卡在首屏最显眼的位置，三个数要同时出现。
拆成三个请求会让首屏多两次网络往返，而且可能出现"同频 8、我的需求加载中"这种割裂状态。

### 8.2 同频圈：从「搭子列表」改成「动态流」

产品定位调整——**同频圈是发日常、动态、视频的地方，不是找搭子的地方**。
（找搭子只有首页那一条路径，「同频一下」按钮也只留在首页。）

在这之前同频圈读的是 `card-list`（搭子需求），和首页是同一个数据源。结果是首页和同频圈长出一模一样的内容，两个 tab 没有存在的理由。

| 数据 | `posts` | 一条动态 = 一段文字 + 最多 3 张图 |

### 11.3 契约

**post-publish**
```

出参 { code: 0, data: { post_id, created_at, today_count } }
```
- 空内容 + 空图直接拒：发出去就是一张空白卡片
- 图片白名单只认 `cloud://` 与 `https://`：不校验协议等于让客户端往文档里塞任意文本，列表页会把它当 `src` 渲染

## 十二、同频圈补评论与删除动态（2026-11-01）

上一轮同频圈改成动态流后留了两个明确缺口，这一轮补齐。三个云函数 + 一个页面，接口契约定死如下。

### 12.1 新增三个云函数

| 函数 | 入参 | 成功返回 | 失败码 |
|---|---|---|---|
| `post-detail` | `{ token?, post_id }` | `data.post{ _id, content, images, media_type, like_count, liked, comment_count, created_at, is_mine, owner{_id,nickname,avatar_url,school,is_verified} }` | 400 缺少动态 id / 404 动态不存在或已被删除 |
| `post-comment` | `{ token?, post_id, action:'list'\|'add', content?, page?, page_size? }` | list → `{ list[{_id,content,created_at,is_mine,owner{...}}], has_more, total, page }`；add → `{ comment_id, comment_count }` | 401 未登录 / 400 说点什么 / 400 评论最多 200 字 / 404 动态不存在或已被删除 |
| `post-delete` | `{ token, post_id }` | `{ ok:true }` | 401 未登录 / 403 只能删除自己发的动态 / 404 动态不存在 |

`post-detail` 的 token 是可选参数：没登录也能看，只是 `liked` / `is_mine` 恒为 false，与 `post-list` 的可选登录口径一致。

### 12.2 三条实现口径（改之前先看这个）

1. **`comment_count` 覆盖写，不做 inc。** 评论 add 之后先 `comments.where({post_id, status: neq('removed')}).count()` 拿真值，再 `posts.doc(id).update({ comment_count })`。inc 一旦哪次漏判重就永久漂移，而覆盖写每次自愈。返回给前端的 `comment_count` 就是这次 count 的结果，与库里一定一致。update 单独包 try/catch——评论已经落库，计数写失败不该让用户以为没发出去。
2. **软删只写 `status:'removed'`，挡在读入口。** 文档还在库里，所以 `post-detail`、`post-comment` 的 getPost、`post-list`、`post-like` 各自都要拦。四处都同时读 `status` 与 `deleted_at`：本项目历史上两种软删写法都有，只读一个会让旧数据漏出去。
3. **`post-delete` 先判已删、再判归属。** 顺序反了的话，重复删除时会把「这条动态存在过」暴露给非本人。

### 12.3 前端：新增动态详情页

`pages/post-detail/post-detail.vue`（704 行）—— 作者行（删除按钮仅 `is_mine` 时出现）→ 全文 → 图片（1 张 420rpx 横幅 / 多张两列，点开全屏）→ 点赞行 → 评论列表 → 底部固定输入框。`pages.json` 注册 `navigationBarTitleText: "动态"`，总页数 29 → 30。

两个容易做错的地方，写在这里免得下次返工：

- **输入框不要自己写 translateY。** `input` 保留默认 `adjust-position`，由平台抬升视口；自己再动一次会和平台顶动叠加成两倍位移。只加 `cursor-spacing: 20`，底部条 `fixed` 且不在滚动容器内。
- **长中文串靠三件套 + `min-width: 0`。** `white-space: pre-wrap` 保留用户换行、`word-break: break-word` 兜老 webview、`overflow-wrap: anywhere` 新引擎接管；真正让它不撑破卡片的是 flex 子项上的 `min-width: 0`，少了这个前三个都白写。

### 12.4 前端：feed.vue 的跳转改造

## 十三、头像上传与同频圈首屏空白（2026-11-01）

### 13.1 新云函数 `user-avatar`

`user-avatar/index.js`（65 行），入参 `{ token, file_id }`，出参 `{ code, msg, data: { avatar } }`。

要单独一个函数的理由：项目里 `user-profile` 是「看别人」的只读接口，`user-me` 是「读我自己」，没有任何一处能写回自己的资料。缺这个入口，前端就只能直连数据库，那样谁也拦不住有人把别人空间的地址写进来。

校验三条：
- `file_id` 必须以 `cloud://` 开头（只收云存储地址，外链会在别人设备上裂图），否则报「头像必须先上传到云存储」
- 长度 ≤ 512
- token 走 `getUserByToken`：查不到、`tokenExpire` 过期、`status==='banned' || status===0` 都拒

写回两个字段：`avatar`（uni-id 标准字段，`user-me` 读它）+ `avatar_url`（本项目自定义字段，`user-profile` 兜底读它）—— 读的地方两个都在用，只写一个就会出现「我的页有、别人看你没有」。

### 13.2 为什么库里存 fileID，不存临时链接

`uniCloud.getTempFileURL` 的链接约 2 小时过期。存临时链接等于第二天所有头像变白框，而且原 fileID 已经丢了，不可逆。所以**存 fileID，展示那侧每次换链**；换链失败退回昵称首字（少张图，不是报错）。

### 13.4 同频圈首屏空白

### 28.2 历史模式的查询怎么拼的

`cloudfunctions/message-list/index.js` 第 218-260 行：

- 锚点：`doc(beforeMessageId)`，取 `created_at = anchorTime`，并校验这条确实属于当前会话；不属于或查不到 → 返回空列表 + `has_more_before = false`（**不退化**成首次加载）。
- 条件：`created_at <= anchorTime`（用 `<=`，同毫秒消息不能漏）+ `_id: dbCmd.neq(beforeMessageId)`。
- 若该会话有 `cleared_at`（用户清过聊天记录），再与 `created_at > clearedAt` 做与运算：`dbCmd.gt(clearedAt).and(dbCmd.lte(anchorTime))`。
- `.orderBy('created_at', 'desc').limit(limit + 1)`，多取的一条只用于判断还有没有更早的；结果 `reverse()` 成升序。

为什么要 `and`：`cleared_at` 之后的记录才允许看，锚点时间之后的记录不属于「更早」，两个条件必须同时成立。这条只在用户清过记录时才走，普通用户走的是单个 `lte`。

### 28.3 历史页不改已读游标

首次与增量会顺手把 `conversation_members.last_read_message_id` 推到最新一条，并把 `unread_count` 清零。历史页**跳过这两件事**：

- 把已读游标改成更早的 `_id`，等于让已读回执倒退，对方那边会重新变成未读；
- 用户只是往回翻了翻，不代表把中间那段都读了。

代码位置：第 341 行与第 346 行的 `if (!isHistory && …)`。这一条是我加的（任务书只要求「不要动既有语义」），因为不改就是 bug。

## 二十九、uni-push 2.0 消息推送（2026-11-03）

### 29.1 新增两个云函数 + 改一个

|---|---|---|---|

### 29.2 user-push 契约

入参：`{ token, action: 'bind' | 'unbind', cid, platform? }`（action 缺省按 bind）

| 出参 | 说明 |
|---|---|
| `{ code:0, msg:'ok', data:{ bound:true, created:true|false } }` | bind 成功；created 表示这次是新插行还是更新旧行 |
| `{ code:0, msg:'ok', data:{ removed:n } }` | unbind；**没 cid / token 过期 / 表不存在全部 code:0** |
| `{ code:401, msg:'未登录' | '登录已过期，请重新登录' }` | 仅 bind 会抛 |
| `{ code:400, msg:'缺少推送标识' | '推送标识不合法' }` | cid 空 / 超 128 字符 |

集合 `push_tokens`（一台设备一行）：

| 字段 | 类型 | 说明 |
|---|---|---|
| _id | string | 自增 |
| user_id | string | uni-id-users._id |
| cid | string | uni-push 客户端标识，非空 ≤128 |
| platform | string | android / ios / ''（其它值一律收敛成 ''） |
| created_at | number | 首次 bind |
| updated_at | number | 每次 bind 刷新 |

**刻意不建唯一索引**：收敛策略是「先 where({user_id, cid}) 查，命中 update、未命中 add」。理由：索引在本项目只是性能项，用户可能还没建，靠索引兜底等于把功能正确性押在一件可选项上。代价是并发 bind 理论上可插两行（只会多推一次，功能无害）。

### 29.3 push-send 契约

入参：`{ token, to_user_id, title, content, payload? }`（**只给服务端内部调用**，前端不要直接调）

出参：`{ code:0, msg:'ok', data:{ sent:n, failed:n } }`；业务拦截 `{ code:403, msg:'你和对方不在同一个会话里' }`、`{ code:400 }`/`{ code:401 }`。

三条关键口径：

1. **不是任意骚扰通道**（`:104-123`）：先取对方的会话列表，再用 `dbCmd.in(hisConvIds)` 反查我在其中哪些里；两条查询搞定，不做 N+1。没有共同会话直接 403，一次推送都不发。
2. **单台失败不影响其它**（`:77-92`）：逐个 cid try/catch，失败只 `console.warn` 并计 failed。
3. **main 恒 code:0**（`:131`）：推送是附加能力，任何异常都不该让「消息已发出」变成报错；只有鉴权 / 成员关系这种业务拦截才 4xx。

SDK 用法（官方文档原文形态）：`const manager = uniCloud.getPushManager({ appId: '__UNI__20CB151' }); await manager.sendMessage({ push_clientid, title, content, payload, force_notification: true })`。

### 29.4 message-send 的新增行为

位置：`:370-401`，在「消息入库 → 未读累加 → 会话预览更新」全部完成之后、`AI 情绪提示` 之前。

| 消息类型 | 推送内容 |
|---|---|
| text | 正文前 40 字 |
| image | [图片] |
| voice | [语音] |
| structured | [约局] |
| share | [动态] |

- 标题：发送者昵称，取不到回落『同频』。

## 四十五、延迟补锚必须到点重判接管（2026-11-04）

### 45.1 问题
§四十四 的接管逻辑上线后，用户反馈「能立即上滑了，但会被拖回来一次」。原因是最新一处补锚定时器（`imgStickTimer`，图片加载完 80ms 后贴底）只在**挂定时器那一刻**判断 `autoStick`，到点不看状态；而接管清理时也没登记它。

### 45.2 结论口径（给以后改这里的人）
- 任何**延迟执行**的滚动动作，到点必须重判 `userTookOver` 与 `autoStick`，不能依赖挂定时器时的判断。
- 任何会改滚动位置的定时器都必须在 `onUserTakeOver()` 里清理。漏一个 = 用户偶发的一次性回弹，且极难复现。
- 适用于 `scroll-into-view` / `scroll-top` / `pageScrollTo` 所有形式。

### 45.3 接口
无变化。纯客户端 `pages/chat/chat.vue`。

### 45.4 上线
无需上传云函数；重新编译 `pages/chat/chat.vue`。验收见 docs/28 §52.5。

## 五十章、学生认证「换校」：契约、配额与后台可见性（2026-11-04）

### 50.1 契约变化表

| 位置 | 变化 |
|---|---|
| `verify-submit` 入参 | 新增可选 `change_school: true`（兼容字符串 true）。不带时的行为与改动前完全一致。 |
| `verify-submit` 出参（action=status） | 新增 `can_change_school` / `change_pending` / `change_school_name`；其余字段一个未改。 |
| `verify_requests` 文档 | 新增 `kind`（`change_school` / `first`）、`from_school_id`。历史文档无这两个字段，按首次认证处理。 |
| `users` 文档 | 换校提交期间只写 `verify_status: pending` + `verify_updated_at`；`is_verified` / `schoolVerified` / `school_id` 保持不变，等 pass 时一起换。 |
| `verify-review` list | `.field()` 白名单补 `kind` / `from_school_id`（这两个字段原先根本没下发）。 |
| `verify-review` detail | 出参 `request.from_school_name`（原学校中文名，查不到为空串）。 |
| `verify-review` reject | `kind = change_school` 时 `verify_status` 还原 `approved`（原先无条件 `rejected`）。 |

### 50.2 为什么 kind / from_school_id 必须落库

换校通过后 `users.school_id` 已被改成新学校，任何「按用户当前学校反推原学校」的做法都只能得到新学校。审核员需要「旧 → 新」的对照，事后追责也需要，所以这两个字段在**提交那一刻**就写进 `verify_requests`。

### 50.3 配额口径（需要后端知晓）

- `MAX_ATTEMPTS = 3`：首次认证的提交次数，按该用户 `verify_requests` **总条数**算（历史行为，未改）。
- `MAX_CHANGES = 3`：换校次数，只数 `kind = change_school` 的条数。
- 两者互不占用：一个被拒过两次首次认证的用户，转校时不会被卡死。
- **被拒也消耗一次换校配额**（当前口径，见 docs/28 §57.9）。若产品要求「被拒不计数」，把 `verify-review/index.js` 里那条 count 的 `where` 改成只数 `status + 非 rejected` 即可，前端不用动。

### 50.4 后台可见性（为什么必须改 list 白名单）

`verify-review` 的 list 用显式 `.field({...})` 白名单取值，不是全文档返回。漏了 `kind / from_school_id` 的后果不是报错，而是后台**静默地**把换校申请当首次认证展示——审核员会拿新材料去比对新学校的名单，而用户材料上写的是旧学校，容易误判。这条经验通用：**凡新增用于判断分支的字段，都要检查 list 白名单是否放行。**

### 50.5 上线清单

1. 上传云函数：`verify-submit`（更新）、`verify-review`（更新）。
2. 重编译前端：`pages/verify/verify.vue`、`pages/verify-admin/verify-admin.vue`。
3. 真机：按 docs/28 §57.8 的 6 条验。
4. 库表：`verify_requests` 无需迁移（新字段只在写入时产生，老文档缺字段按首次认证处理）。

### 50.6 限制

- 换校的旧申请与换校后的新申请会同时处于 `approved`，后台「已通过」tab 会列出两条，看起来像重复；本轮不做历史分组。
- 后台列表只标「换校」，不显示旧校名（旧校名在详情与 pass 弹窗里）。
- 换校没有冷却期，只有 3 次上限；刷审核由人工兜底。
