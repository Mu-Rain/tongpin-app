# 长会话工程纪律（缓存命中率 + 上下文体积）

> 这份提示词给我自己看，覆盖我在这类长项目里的默认写作与工具习惯。
> 适用于：uni-app / uniCloud 这类多文件、长周期、靠压缩续命的项目。
> **优先级高于我的默认习惯。若与我的本能冲突，以此为准。**

---

## 0. 先理解为什么

长会话的成本由两件事决定，它们**不是一回事**，别混着优化：

| 指标 | 由什么决定 | 优化手段 |
|---|---|---|
| **缓存命中率** | 已发过的历史**是否被动过** | 不动历史 |
| **上下文体积** | 每轮新增多少内容 | 少贴、压缩、外置 |

命中率低通常不是因为体积大。实测数据（一个 925 请求、1.03 亿 token 的会话，命中率 86.6%）：

| 失效原因 | 次数 | 丢失 token | 占比 |
|---|---|---|---|
| `clientInserts` 客户端中途改写历史 | 74 | 6,064,129 | **44%** |
| seam 接缝断裂 | 35 | 2,324,551 | 17% |
| providerSide 上游侧 | 24 | 2,088,567 | 15% |
| switch / restart / rewind | 3 | 452,013 | 3% |

bili 的日志原文把这 44% 定性得很清楚：

> `client-side mid-history rewrite … the client's resent history diverged at inbound message[k] … the wire break is the host's own churn, not a bili rebuild`

**结论：最大的泄漏是「我自己在对话中途改了已发出去的历史」。**

---

## 1. 铁律：不碰已发出的历史

这是**最高优先级**，比少贴代码重要得多。

| 禁止 | 为什么 |
|---|---|
| 往回改之前轮次的内容 | 一旦中途改写，从改写点往前的前缀缓存全部作废 |
| 让注入的系统提示/环境上下文中途变化 | 同上 |
| 中途切换 provider / 模型 / 密钥 | bili 记为 `switchMissed` / `keySwitchMissed` |
| 中断（abort）后继续同一轮 | bili 记为 `abortCorrelated`，那一轮的缓存全丢 |

**要改就往后加，不要往回改。** 发现前面写错了，就新写一条「上一条第 X 点更正为……」，不要原地返回去改。

---

## 2. 工具调用的写法

### 2.1 代码改动：只报「文件:行号 + 改了什么」

❌ 不要这样做：

```
我把 `doSend` 改成这样：
```js
async doSend() {
  const payload = { ... };
  // ... 30 行
}
```
```

✅ 这样做：

```
`app/pages/chat/chat.vue:747-822` — doSend 里乐观气泡补 `duration`/`recalled` 两个字段，
`transport.send()` 透传 `duration`；失败分支保持原样。
```

**例外**：只有当我需要**精确对照某个易错片段**（比如引号嵌套、正则转义）时才贴，且只贴那 3–5 行。

### 2.2 测试脚本：不进对话

❌ 不要把脚本源码写进工具参数再看输出。

✅ 这样做：

- 用 `run_code` 时，脚本里**只 print 失败项和总数**，成功项不打印
- 断言格式统一为 `PASS 42 / 42` 或 `FAIL 3/42: [用例名] 期望 X 实际 Y`
- 临时文件跑完立刻删，**不要在回复里复述脚本内容**

### 2.3 读文件：读区间，不读全文

❌ 不要对大文件 `read` 全文然后靠上下文记着。

✅ 用 `offset` + `limit` 只取相关区间；需要全貌时先用 `grep` 定位行号再精读。

### 2.4 命令输出：避免大块打印

❌ `Get-ChildItem -Recurse` 全量列表、`git diff` 整段、`node --check` 逐个文件的成功回显。

✅ 只打印**数量、失败项、异常项**。成功一律静默。

---

## 3. 项目事实外置到文件，不要重复复述

**不要**每轮重发「项目路径 / 58 个云函数 / 33 份文档 / 13 条踩坑」这类稳定事实。

**要**把它们维护在工作区的文件里，需要时**引用路径**：

| 事实类型 | 放哪里 |
|---|---|
| 项目全貌、进度、踩坑 | `dazi-app/docs/*-会话交接.md` / `*-进度交接.md` |
| 接口契约 | `dazi-app/docs/*-契约.md` |
| 部署清单 | `dazi-app/docs/*-部署清单-*.md` |

**每轮开头只需要一句**：「按 `docs/28-业务逻辑改动说明.md` 继续」，而不是复述它的内容。

新增稳定事实时，**追加到对应文档**，然后在对话里只说「已写入 X 文档第 N 节」。

## 4. 压缩纪律（管体积）

bili 的实际可用窗口是 **872,000**（原生 1,000,000 减输出预留 128,000）。

| 上下文达到 | 动作 |
|---|---|
| **40 万** | 主动发一次「压缩上下文」 |
| **55 万** | 再压一次，并考虑开新会话 |
| **65 万** | bili 会自动提醒 —— **别等到这里** |

### 压缩时的策略（bili 源码里的原话）

> 压缩时**优先选更小、更靠尾部**的范围 —— 压缩最近的大块内容，**保留稳定前缀（最早的几条消息）不动**。一次大改写会让请求形态突变，可能触发上游风控；小而靠尾部的折叠能让前缀缓存活下来。

**所以：一次只压一小段，从尾部说起，别一次把整个历史折掉。**

### 压缩后必须检查

如果压完体积**没有明显下降**（比如压完还接近原值），这是会话即将报废的征兆 —— **立刻开新会话**，别再继续。

---

## 5. 每轮回复的结构

固定用这个顺序，减少冗余：

1. **结论**（1–2 句）
2. **改了什么**（文件:行号 + 一句话，不贴代码）
3. **验证**（`PASS n/n` 或失败项）
4. **下一步**（或需要用户决定的事项）

不要写：过程回顾、重复我已经说过的话、自我表扬、把上一条内容再复述一遍。

---

## 6. 何时开新会话

| 情况 | 动作 |
|---|---|
| 任务告一段落（一个功能验收完） | 开新会话，先读交接文档 |
| 上下文过 55 万 | 开新会话 |
| 压缩后体积不降 | **立刻**开新会话 |
| 连续 20+ 轮在同一话题里挖 | 开新会话 |

**开新会话不是失败，是纪律。** 成本是几分钟读交接文档，收益是避免几天的成果卡死在一条会话里。

---

## 7. 绝对不要做

| 禁止 | 后果 |
|---|---|
| 用「派生 / 续接」开新会话 | 全量继承父会话历史，上百万 token 立刻再死 |
| 弹有时限的问题框 | 超时会把用户没说完的话弄丢（已发生过两次） |
| 中途改已发出的历史 | 前缀缓存全废（占缓存丢失的 44%） |
| 为了省事贴整段代码 | 体积涨、命中率不动，两头亏 |
| 开了 `BILI_ALLOW_DSH_COMPACTION` 还继续用旧会话 | checkpoint 永久覆盖原始历史 |

---

## 8. 自检（每轮结束前问自己）

1. 我这一轮**有没有动过之前已经发出去的内容**？
2. 我有没有贴超过 10 行的代码？
3. 我有没有把测试脚本源码写进对话？
4. 我有没有重复复述项目里已经写在文档中的事实？
5. 上下文到 40 万了吗？到了就该压。

---
