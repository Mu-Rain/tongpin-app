## 1. 原会话为什么死了（技术结论，别再重复踩）

| 项 | 实测值 |
|---|---|
| 会话 ID | `session-8329f4b9-2dbb-40d5-ab7f-64ef94d404fa` |
| 是否派生 | `isSeeded=false`、`inheritedEventCount=0`（是纯新会话，没继承） |
| 最终上下文 | **1,549,063 / 1,000,000 token（155%）** |
| 轮次 / 步数 | 58 轮 / 1135 步 |
| 工具调用 | 1078 次，全部是 `run_code`（PTC 模式） |
| DSH 原生压缩 | **642 次尝试，642 次失败**（全部 422） |
| bili 折叠 | 35 个块，16 个生效，折完估算仍 **1,311,956 token** |
| 最终死因 | `400 workbuddy upstream client: 内容过长，请精简或新建任务` |

### 死锁链条（这是关键认知）

```
DSH 想压缩  →  bili 拒绝（422 dsh_compaction_refused：bili owns compression on this lane）
            →  bili 自己折叠 → 折完 131 万，仍超上游上限
            →  请求原样发出 → 上游 400
```

**两条压缩路都走不通**：DSH 的被 bili 封死，bili 的折不够。这不是配置写错，是架构层面的死锁。

### 那条 422 的原文（将来排障用）

> `dsh native compaction call refused by billion-context: bili owns compression on this lane (#1729, cf. #1772/#1206). A landed dsh compaction checkpoint durably shadows the raw conversation history, which destroys the proxy's compression substrate. To run dsh native compaction on this lane anyway, opt in explicitly: "allowDshCompaction": true in the bili config or env BILI_ALLOW_DSH_COMPACTION=1 (#2028).`

### 已经做过的抢救动作（记录，避免重复劳动）

- 曾设 `ACP_COMPRESS_NUDGE=0` 关闭 bili 提醒注入 —— **无效**，它只管"要不要提醒模型压缩"，不管折叠本身
- bili 的 `externalSummary`（独立摘要模型）默认关闭，要启用需要一个标准 API Key 接口（智谱 / DeepSeek 官方等）；
  现有三个渠道（trae / workbuddy / buddy）都是插件托管的登录型，没有可手填的 `baseUrl + Key`，所以这条路当时没走通
- 唯一能放开 DSH 原生压缩的开关是 `BILI_ALLOW_DSH_COMPACTION=1`，代价是 **checkpoint 永久覆盖原始历史**

### 4.3 ★★ B 组顺手修的 pre-existing bug（务必知晓）

`message-conversations/index.js:155-166` 的 `relMap` key **没有归一化**，而拼装时查的是归一化过的 `pairKeyStr`（小 id 在前）。

- 原代码：`const key = r.user_a_id + '|' + r.user_b_id`（HEAD 里就有，不是新引入的）
- 后果：**`buddy_tags` / `buddy_tag` / `buddy_tag_color` / `pin_locked` 只对「我 _id 字典序较小」的一半用户生效**
- 实测证据（同一份数据，只换 id 顺序）：
  - `me=u_a other=u_me` → `pin_locked=true`, tags 有值
  - `me=u_me other=u_a` → `pin_locked=false`, tags 空
- 修法：`:157-166` 改成 `ra < rb ? ra+'|'+rb : rb+'|'+ra`，并对空值 continue

**这条会直接影响「清空的搭子会话应该排在前面」的需求是否成立，接手时务必确认它在位。**

## 7. 13 条铁律（从 `11-会话交接单.md` §4 继承，违反即白屏/静默失败）

1. `.vue` 模板**不能**直接用 `<script>` 顶层 `const`/`function` —— 必须挂进 `data` 或用 `this.`
2. HTML 注释里**不能**写 `<script>` 字面量
3. 模板里引用的每个标识符都必须有声明（`data` / `computed` / `methods`）
4. `methods` 里调用其他方法**必须带 `this.`**
5. 模板里**不能**用 `.prevent`
6. 白名单必须同步补字段
7. 一对多关系的唯一性建在**主体**上，不建在事件上
8. 云函数表不存在时**静默降级**，但登录表（`uni-id-users`）缺失要返回 500
9. 云函数必须 `node --check` 通过才能交付
10. 前端 `.vue` 改完必须抽 `script` 段单独 `node --check`
11. 交付必须带**可复现的验证证据**（断言数、通过数、失败数）
12. **不采信子代理的自报** —— 父 agent 必须逐行核实代码
13. **面向用户全程中文**（含工具调用时填写的那行说明）

## 8. ★ 上下文压缩纪律（新会话必读，血的教训）

> 这一节是 2026-10-22 复盘后新增的。旧会话不是死于「窗口太小」，而是死于**一路涨到 bili 折叠跟不上**。
> 调参数救不了，只有节奏能救。

### 8.1 先记住三个数

| 项 | 值 | 来源 |
|---|---|---|
| 模型原生窗口 | **1,000,000** | 模型声明（`lastWindowResolution.b`） |
| 输出预留 | **128,000** | `outputBudgetHighWater` |
| **bili 实际生效窗口** | **872,000** | `1000000 − 128000` |

计算公式（bili 源码 `reserveOutputHeadroom`）：

```js
const reserved = Math.min(maxOutput, capPct * window);
return window - reserved;   // 1000000 - 128000 = 872000
```

**872,000 是保护值，不是限制值** —— 它保证模型还有 12.8 万 token 能写回复。别去调大它。

### 8.2 手动压缩节奏（照做）

| 上下文达到 | 占 872k 比例 | 动作 |
|---|---|---|
| **40 万** | 46% | 主动发一次「压缩上下文」 |
| **55 万** | 63% | 再压一次，并开始考虑开新会话 |
| **65 万** | 75% | bili 会自动提醒 —— **别等到这里** |

bili 的自动提醒阈值是窗口的 75%（`compress.maxContextLimit` 默认 `"75%"`），也就是约 **654,000 token**。等它提醒，说明已经用掉四分之三了。

### 8.3 为什么不能靠调大窗口

| 你调大窗口后 | 实际后果 |
|---|---|
| nudge 提醒更晚触发 | 上下文涨得更狠才压缩 |
| 折叠块更大 | 单次压缩更慢、更容易失败 |
| 上游真实上限没变 | 到点还是 400 |

旧会话的死因链条（见 §1）是：**DSH 原生压缩被 bili 拦（642 次 422）→ bili 自己折叠 → 折完仍 131 万 → 上游 400**。
把分母调大只会把「131 万」这个数字往后推，不会消除它。

### 8.4 三条硬规矩

1. **看到上下文过 40 万，主动压缩**，不要等 bili 提醒。
2. **压缩后如果发现没降下来**（比如压完还接近原值），立刻开新会话 —— 这正是旧会话的死前征兆。
3. **任务告一段落就开新会话**，别在一个会话里连续做几十轮。会话不是越长寿越好。

### 8.5 如果要改窗口（不推荐，仅供知道）

配置文件 `C:\Users\lenov\.config\billion-context\billion-context.json`：

```json
{
  "providers": {},
  "compress": {
    "modelContextLimit": 872000,
    "outputHeadroomMaxPct": 0.25
  }
}
```

- `compress.modelContextLimit` —— 窗口来源里**优先级最高**，直接指定分母，绕开上面的减法
- `compress.outputHeadroomMaxPct` —— 预留比例，默认 0.25（25%）

**改完必须完全退出 DSH（托盘右键退出）再启动。**

### 11.3 三个设计决定（当时为什么这么定）

1. **搭子「完成一次」不动 `status`**，只累加 `done_count` + 清掉 `done_a`/`done_b`。理由：`buddy-list` 默认只查 `active`，加 `completed` 状态会让搭完的关系从搭子页消失——同学搭子是长期可复用的。

3. **不引入共享模块**：41 个云函数每个目录只有 `index.js` + `package.json`，没有公共目录。所以 credit 核心（读分/查规则/写流水/封顶）在每个用到的云函数里各内联一份，**以 `credit-list` 那份为准**。改逻辑要四处一起改。

### 11.4 保护点（改之前先看懂，别拆了）

- **幂等**：`verify-review` 的 `hasVerifyPass()` —— 同一个人有过 `verify_pass` 流水就不再给分；`buddy-complete` 自己点过直接返回、不再给分。

- **降级**：两张新表不存在时全部静默降级——`credit-list` 返回 80 分 + 内置 4 条规则 + 空列表；`buddy-complete` / `report-review` / `verify-review` 的给分失败只 `console.warn`，不影响主业务结论。
- **双字段兼容**：`credit_score` 与 `credit` 历史数据都有人写，读一律 `pickInt(u.credit_score, pickInt(u.credit, 80))`，写两个都写。

### 12.2 本轮只做 3 个「易得」称号

| code | 名字 | 判定（三项都在 `title-list` 里做，缺一不给） |

### 12.3 三个设计决定（为什么这么写）

1. **`user_titles.title_id` 存 `titles.code` 字符串，不存 `_id`** —— `titles` 表本轮可以是空的，用户不必先去后台插数据；存 code 才能在表空时照常工作，将来后台改名字/改文案也不用迁移已获得记录。
2. **评估与补发全部集中在 `title-list`，不碰 `verify-review` / `buddy-complete`** —— 那两个刚做完信誉系统并已真机验收通过，不动风险最小。代价：新称号要等用户进「我的」或称号墙才拿得到。
3. **`first_buddy` 用并集判定（流水或完成计数）** —— 只认流水会漏两种真搭成过的人：给分时 `applyCredit` 抛错（`done_count` 已 +1 但流水没写）、流水表被清理过的老用户。

### 12.4 降级与保护点

- `titles` 表不存在 → 回落到代码内置的 3 条，照常返回（不 500）。
- `user_titles` 表读不到 → 连补发都跳过（插不进去，`newly` 也不假装发了）。
- 并发进页面 → `(user_id, title_id)` 唯一索引挡下后到那次，不记 `newly`，不重复发。
- 并发点佩戴 → 先全置 false 再置 true，两次 update 之间不会出现「两条同时佩戴中」的稳定态。
- 前端：`credit-list`/`title-list` 还没部署时，页面一律降级为空态 + 「稍后再试」，不白屏、不卡 loading。

### 12.5 上传后怎么验（4 步）

### 13.2 百科三态（`src` 由云函数给，前端照它渲染）

| `src` | 含义 | 首页表现 |
|---|---|---|
| `today` | 今天那条 | 标题 + 正文（超 3 行折叠）+ 分类 + 日期 |
| `latest` | 今天没有，回落到最近一条 | **照常显示** + 灰色「往期」标 + 它自己的日期（不冒充今天） |
| `none` | 一条都没有 | 「今日百科还没更新」+「明天再看看」 |

取数失败（没部署 / 超时 8s / `code!==0` / H5 无 uniCloud）→ 静默降级成改造前的静态占位，不弹红、不卡 loading。

**「今天」按北京时间算**：服务器跑 UTC，直接取 UTC 日期会在早上 8 点前算成昨天，必须 `new Date(Date.now() + 8*3600*1000).toISOString().slice(0,10)`。

### 13.3 ★ 这次抓到的集成缺陷（教训，同类问题以后还会遇到）

两侧**各自严格照契约实现，合起来功能是死的**：

- 云函数侧按契约把 seed 的 7 条 `publish_date` 写成空串，靠「最近一条」回落 → `src='latest'`
- 前端侧按契约把 `src !== 'today'` 一律当「今天没更新」→ 空态

**结果：灌完 seed 首页永远显示「今日百科还没更新」，答辩当天就是一张空卡。**

两个子代理都没发现，因为各自的边界里都没错。这正是「各自通过 ≠ 整体联调通过」的典型。
最终口径改为「`latest` 照常显示 + 标往期」，并把 seed 的 `publish_date` 改成**灌入当天（北京时间）**（灌完就是 `today`，第二天自动变「往期」）。

> **纪律**：以后凡是「A 侧产出某字段、B 侧消费该字段」的地方，验收时必须把两侧对着**同一个具体取值**走一遍，不能只看各自的四态表。

### 13.3.1 修正过程里的第二个坑：唯一索引把「全写今天」挡了

第一次修的时候我给的方案是「7 条全写今天」，但 `encyclopedia.publish_date` 上有**唯一索引**（§1 为「一天一条」立的），同值必然冲突：

| 方案 | 实测结果 |
|---|---|
| 全空串（最初） | `inserted=1 skipped=6` —— 只进 1 条 |
| 全写今天（我给的方案） | `inserted=1 skipped=6` —— **同样是只进 1 条** |
| **今天起往前错开 7 天**（最终采用） | `inserted=7 skipped=0` ✅ |

最终 `encyclopedia-seed/index.js:27-29` 加了 `bjDate(offsetDays)`（今天 +8h 取日期，减 offsetDays 得前 N 天），`:112` 用 `bjDate(i)` 写日期。第 1 条是今天 → 当天 `src='today'`；其余 6 条成为真实往期，明天起 `latest` 有内容可标「往期」。

> **第二个纪律**：**加唯一索引之前，先想清楚「批量插入的数据是不是同值」**。这次空串和「全今天」都栽在同一个点上，症状还都是「静默只进 1 条」，不报错就发现不了。

### 13.4 上传后怎么验（5 步）

1. 传完 `encyclopedia-daily` 后打开首页 → 百科卡显示「今日百科还没更新」（表是空的，这是对的）。
2. 云函数列表点 `encyclopedia-seed` → 测试运行 → 入参 `{}` → 返回 `{"inserted":7,"updated":0,"skipped":0}`（已有旧数据时会返回 `updated` 计数）。
3. 再回首页下拉刷新 → 应显示一篇百科，**没有**「往期」标（今天是灌入日）。
4. 把 `encyclopedia` 里那几条的 `publish_date` 改成昨天 → 刷新 → 内容照常显示，右上角出现灰色「往期」。
5. 进对方主页 → 资料卡下有「TA 的称号 ›」→ 点进去标题是「TA 的称号」，点已获得的卡片提示「称号只能本人佩戴」，**不会**改对方数据。

### 14.7 上下文压缩纪律修正（本轮实测）

**结论：压缩太频繁反而是缓存命中率的杀手。**「阶段完成立刻压缩」对小阶段会变成「每完成一小步压一次」，累计十几次全额重付。

**修正后的做法**：不按「阶段」压，按「体积」压 —— 攒到可压缩量足够大（如 50K 以上）再一次性压多个 range，且一次 `compress` 调用压多个范围。`acp_status` 提示 `max compressible < threshold` 时就别压。

### 15.5 上传后怎么验（4 条）

1. **日历 ↔ 记录**：`history` 页有 N 条记录，日历上那些天必须都亮；某天亮但 history 没有那天 → 失败。
2. **日历 ↔ 首页**：日历顶部「连续 N 天」必须与健身首页那个数字**完全一致**。
3. **提醒 ↔ 打卡**：设 20:00，现在已过点且今天没练 → 首页出现提示条；练完一次再刷新 → 消失。
4. **提醒 ↔ 静默**：点「今天不再提醒」→ 重启 App → 当天不再出现。

### 15.6 本轮遗留

- 提醒**不是系统推送**，要用户主动打开 App 才会看到（见 §15.2 第 3 条）。
