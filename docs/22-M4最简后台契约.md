## 2. 四个云函数

四个都遵循：
- 目录自包含（只有 `index.js` + `package.json`），**不许 `require` 目录外的东西**，共用逻辑内联复制（母本是 `verify-review/index.js` 的 getUserByToken + isAdmin 段）
- 业务错误走 `code` 不 `throw`：`catch` 里 `return { code: e.bizCode || 500, msg: e.message }`
- 表不存在时静默降级；拿不到当前用户返回 500

### 2.1 `admin-reports`（新建）

**入参**：`{ token, action: 'list' | 'decide', status?, page?, page_size?, report_id?, decision?, reason? }`

**出参（list）**：
```json
{ "code":0, "data": { "list":[{
    "_id":"…", "reporter_id":"…", "reporter_name":"同学A",
    "target_type":"user", "target_id":"…", "target_name":"同学B",
    "reason":"harassment", "reason_text":"骚扰他人", "detail":"…",
    "status":"pending", "created_at":1760000000000 }],
  "total":12, "pending_count":3 } }
```

**出参（decide）**：`{ code:0, data: { report_id, status, credit_delta } }`

- `list`：`status` 不传默认只看 `pending`；按 `created_at` 倒序；`page_size` 上限 50。
- `decide`：`decision` ∈ `upheld` / `dismissed`。**内部直接复用已有 `report-review` 的处置逻辑**（带 `status:'pending'` 条件的原子 update 抢占 → 409），扣分规则不动。
- 处置后**不物理删除**，只改状态。

> 为什么单独建 `admin-reports` 而不让前端直接调 `report-review`？因为后者只管「处置一条」，没有列表能力；而列表要 join 出举报人/被举报人昵称（白名单字段，不能外泄手机号）。两个函数职责分开，report-review 保持已验收状态不动。

### 2.2 `admin-users`（新建）

**入参**：`{ token, action: 'list' | 'ban' | 'unban', keyword?, school?, verify_status?, credit_band?, page?, page_size?, user_id? }`

**出参（list）**：
```json
{ "code":0, "data": { "list":[{
    "user_id":"…", "nickname":"…", "user_no":"…", "avatar":"",
    "school":"…", "is_verified":false, "credit_score":82,
    "status":"normal", "created_at":1760000000000 }],
  "total":37, "page":1 } }
```

**出参（ban/unban）**：`{ code:0, data: { user_id, status: "banned" | "normal" } }`

- `keyword`：匹配 `nickname` 或 `user_no`（用 `dbCmd.or` + 转义后的正则，**必须复用 `message-search/index.js` 的 `escapeReg` 写法**，否则用户输入 `.*` 会全表扫）。
- `credit_band`：`low`(<60) / `mid`(60-79) / `high`(≥80)，三选一，不传不筛。
- `verify_status`：`verified` / `unverified`。
- **返回的白名单**：绝对不能带 `phone` / `password_hash` / `token`。
- `ban`：写 `users.status = 'banned'`、`ban_at = now`。**不允许封禁自己**（400），**不允许封禁另一个管理员**（403）。
- `unban`：写 `status = 'normal'`、`ban_at = 0`。

### 2.3 `admin-encyclopedia`（新建）

**入参**：`{ token, action: 'list' | 'create' | 'update' | 'remove', id?, title?, content?, category?, publish_date?, active? }`

**出参（list）**：`{ code:0, data: { list: [ {_id, title, content, category, publish_date, active, created_at} ], total } }`
**出参（create/update/remove）**：`{ code:0, data: { _id } }`

- `category` 白名单：`study` / `health` / `life` / `campus`。
- `publish_date` 格式必须 `YYYY-MM-DD`；**有空串也可以**（表示「不指定日期，走回落」）。
- **唯一性检查**：`create`/`update` 时若 `publish_date` 非空且已被**别的条目**占用 → `409`「这一天已经有百科了」。**不能靠唯一索引报错来兜**（现在那条索引可能没建，报错信息也不友好）。
- `remove`：**软删**（`active = false`），不物理删。物理删会让已经看过的人下次打开报「不存在」。
- `title` / `content` 不能为空（`400`）。

### 2.4 `admin-titles`（新建）

**入参**：`{ token, action: 'list' | 'update', code?, name?, desc?, rarity?, condition_text?, active?, sort? }`

**出参（list）**：`{ code:0, data: { list: [ {code, name, desc, rarity, condition_text, active, sort, source} ], total } }`
**出参（update）**：`{ code:0, data: { code } }`

- `list` 必须**把代码内置的 3 条也列出来**（`source: 'builtin'`），表里的标 `source: 'table'`。理由：管理员要能改内置 3 条的文案，而不是面对一个空列表。
- `update` 的语义是 **upsert**：表里没有这个 `code` 就 `add` 一条（`source` 变 `table`），有就 `update`。这样「改内置称号的文案」才成立。
- `rarity` 白名单：`common` / `rare` / `epic`。
- 只做 `update`（upsert），**不做删除**：内置 3 条删不掉；要停用就 `active=false`（`title-list` 已有回落逻辑）。
- `code` 不可改（它是 `user_titles.title_id` 存的键）。

## 3. 前端：四个页面 + 一个入口

### 3.1 页面与路由

```
pages/admin-reports/admin-reports        举报处理
pages/admin-users/admin-users            用户列表
pages/admin-encyclopedia/...             百科配置
pages/admin-titles/admin-titles          称号配置
```

`pages.json` 追加 4 条（第 27-30 条），**tabBar 4 项一个字都不许动**。

### 3.2 入口（`mine.vue` 的管理员区块）

现在那里只有一个「认证审核」。改成**四个入口一列**：

```
认证审核 (N)      ← 已有，不动
举报处理 (N)      ← 待处理数，无则显示「举报处理」
用户列表
百科与称号        ← 两个配置页合并成一个入口，进去再分两个 tab
```

> 为什么百科和称号合并一个入口：两个都是「内容维护」，单个条目很少，拆两个入口会让管理员区块变成 5 行，手机上太长。合并后用 tab 切换。

### 3.3 四个页面共同要求

- **非管理员**：进来先看到「没有权限」空态，与 `verify-admin.vue:4-8` 同款，**不要先发请求再报错**。
- 四态齐全：加载中 / 空 / 出错 / 正常。
- 每个操作成功后**原地更新列表**，不整页重拉。
- 危险操作（封禁、处置成 upheld、软删百科）必须 `uni.showModal` 二次确认。
- 样式照抄 `verify-admin.vue`（同一套 `.tabs` / `.item` / `.deny` 命名与配色变量）。

### 3.4 举报处理页

- 顶部 tab：待处理 / 已成立 / 已驳回。
- 每条：举报人昵称 → 被举报人昵称（或「卡片」「消息」）、原因中文、补充说明、时间。
- 点开详情 → 底部两个按钮「成立（扣 10 分）」「驳回」。
- `upheld` 且目标是 user 时，确认弹窗里要写明**「将扣除对方 10 信誉分」**。
- 处置成功 → 从待处理列表移除。

### 3.5 用户列表页

- 搜索框（昵称 / 用户号）+ 三个筛选（学校 / 认证状态 / 信誉段）。
- 每条：头像、昵称、用户号、学校、认证标记、信誉分、当前状态（封禁的显示红标）。
- 点开 → 底部「封禁」/「解封」。确认弹窗写清「封禁后该用户无法登录、无法发布」。

### 3.6 百科配置页

- 列表：标题、分类、日期、启用状态。
- 新增 / 编辑：标题、正文（多行）、分类选择、日期（可留空）。
- 「删除」= 停用，文案用「停用」而不是「删除」。
- 正文长度不设下限，但**超过 72 字才在首页出现「展开」按钮**，页面上给一句提示。

### 3.7 称号配置页

- 列表：code、名字、稀有度、条件文案、启用状态、来源（内置/自定义）。
- 点开可改：名字、描述、稀有度、条件文案、启用、排序。`code` 只读。
- 保存即 upsert。

## 4. ★ 联调验收点（上一轮踩过的坑，必须两侧对着同一取值验）

**百科配置 + 首页**：管理员在配置页新增一条 `publish_date` = 今天的百科 → 回首页刷新 → **必须**能看到这条，且 `src='today'`、**没有**「往期」标。

**称号配置 + 称号墙**：管理员把 `profile_complete` 的 `condition_text` 改成一句话 → 进称号墙 → 该条未获得时显示的**必须**是新文案。

**举报处理 + 信誉分**：处置成 upheld（目标是 user）→ 该用户 `credit_events` 多一条 `delta=-10` → 他的信誉页分数减 10。

**用户列表 + 登录**：封禁某人 → 该账号 `user-login` 返回 2003「账号已被封禁」。
