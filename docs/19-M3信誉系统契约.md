## 1. 可升级性怎么落地（这是用户点名的硬约束）

**规则与执行分离**：
- 分值、文案、开关都存在 `credit_rules` 集合里，字段：`code`(string, 唯一)、`delta`(int)、`text`(string)、`active`(bool)、`created_at`(long)。
- 云函数**按 `reason_code` 查这张表**拿 delta；**查不到、表不存在、或 `active=false` 时回落到代码内置默认表**。
- 将来要加事件类型 / 调分值 / 改文案：只改数据，不改代码、不用重新上传云函数。

**内置默认表（代码里的兜底，必须与本节完全一致）**：

| code | delta | text |
|---|---|---|
| `buddy_done` | +2 | 完成一次搭子 |
| `no_show` | −5 | 放鸽子 |
| `report_upheld` | −10 | 举报被核实 |
| `verify_pass` | +5 | 通过学生认证 |
| `admin_adjust` | 0 | 管理员调整 |

分数口径：初始 **80**，上限 **100**，下限 **0**。等级：`<60` 受限 / `60-79` 正常 / `80-89` 良好 / `90-100` 优秀。

> ⚠️ **项目现实约束**：本仓库 41 个云函数**每个目录只有 `index.js` + `package.json`，没有任何共享模块**。所以 credit 核心逻辑（默认表 + 写流水 + 改分）要在每个用得上的云函数里各内联一份。**以 `credit-list/index.js` 里的那份为准**，其余 3 个函数复制同一段代码，不要各写各的。

## 2. 集合与字段

### 2.1 `credit_events`（新增）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 自动 |
| `user_id` | string | 被加/扣分的人 |
| `delta` | int | 本次变化，+2 / −5 / −10 / +5 |
| `reason_code` | string | 见 §1 表 |
| `reason_text` | string | 写入时的文案**快照**（后台改文案不影响历史记录） |
| `score_after` | int | 变化后的分数 |
| `ref_id` | string | 关联对象 id（搭子关系 id / 认证申请 id / 举报 id），可空串 |
| `created_at` | long | 毫秒时间戳 |

索引：`idx_user_time` on `(user_id ↑, created_at ↓)`（非唯一）。

### 2.2 `credit_rules`（新增）

字段见 §1。索引：`idx_code` on `code ↑`（**唯一**）。

### 2.3 `buddy_relations`（加 4 个字段，不改 status 枚举）

| 字段 | 类型 | 说明 |
|---|---|---|
| `done_a` | bool | user_a 那一方点了「这次搭完了」 |
| `done_b` | bool | user_b 那一方点了 |
| `done_count` | int | 累计完成次数，初始 0 |
| `last_done_at` | long | 上次双方确认完成的时间，初始 0 |

**为什么不动 `status`**：`status` 只有 `pending / active / ended` 三值，且 `buddy-list` 默认只查 `active`。加 `completed` 会让搭完的关系从搭子页消失，而同学之间的搭子关系是长期的、要能反复搭。所以「完成一次」用计数器表达，关系保持 `active`。

## 3. 云函数契约

### 3.1 `credit-list`（新建，任何登录用户）

**入参**：`{ token, page?=1, page_size?=20 }`（page_size 上限 50）

**出参**：
```json
{ "code": 0, "msg": "ok", "data": {
  "score": 82, "level": "good", "level_text": "良好",
  "can_publish": true,
  "rules": [{ "code": "buddy_done", "delta": 2, "text": "完成一次搭子" }],
  "list": [{ "_id": "…", "delta": 2, "reason_code": "buddy_done",
             "reason_text": "完成一次搭子", "score_after": 82, "created_at": 1698000000000 }],
  "total": 12, "page": 1, "page_size": 20 } }
```
- `score` 取 `users` 表的 `credit_score`，缺失回落 `credit`，再缺失回落 **80**（与全项目 `pickInt(u.credit_score, pickInt(u.credit, 80))` 口径一致）。
- `rules` 返回的是**当前生效规则**（`credit_rules` 有数据就用表，没有就用内置默认表），供前端画「怎么算的」。`admin_adjust` 不出现在 `rules` 里（不是用户可见事件）。
- `level` 取值：`limited` / `normal` / `good` / `excellent`。
- 明细按 `created_at` 降序。

### 3.2 `buddy-complete`（新建，任何登录用户）

**入参**：`{ token, relation_id }`

**出参**：
```json
{ "code": 0, "msg": "ok", "data": {
  "relation_id": "…", "my_done": true, "peer_done": false,
  "done_count": 0, "rewarded": false,
  "credit": { "score": 82, "delta": 0 } } }
```
- 只有这段关系的当事人（`user_a_id` 或 `user_b_id` 等于自己）能调，否则 **403**。
- 关系 `status` 必须是 `active`，否则 **409**。
- 自己已经点过 → **幂等**，直接返回当前状态，`rewarded=false`，不重复加分。
- 并发保护（实现时补的一条）：结算那一步用**条件原子更新**（`_id` + 对方未确认标记仍为 `true` + 自己未确认 ≠ `true`）抢占，只有 `affectedDocs > 0` 才加双方的分；没抢到的那次走幂等分支。返回的 `my_done`/`peer_done` 取**结算后的真实状态**（结算会把双方标记清零），不要硬写 `true`，否则弱网双发时输的一方会看到错误的「等对方」。
- 双方都点过 → `done_count + 1`、`last_done_at = now`、两个 `done_` 位清 false、**双方各 +2**（`reason_code='buddy_done'`），此时返回 `rewarded=true`、`done_count` 为新值、`credit.delta=2`、`credit.score` 为自己加后的分。
- 双方各 +2 是两次独立写流水（各自一行 `credit_events`）；**任何一方写失败不影响另一方的那条已经写的**——不追求跨用户事务。
- **结算必须原子抢占**：结算用带条件的 `where({_id, 对方位: true, 自己位: dbCmd.neq(true)}).update(...)`，只有 `updated > 0` 的那一个请求继续走两次给分。理由：两个人同时点、或同一个人弱网重发两次，都会读到「对方已确认 + 自己没点」，先读后无条件写会让 `done_count` 加两次、双方各拿两轮分。
- **没抢到的请求**返回**结算后的真实状态**（`my_done=false`、`peer_done=false`、`done_count` 为新值、`rewarded=false`、`credit.delta=0`），**不是**字面的 `my_done=true`。理由：结算已经把两个 `done_` 位清 false，硬写 `true` 会让这一侧看到「已确认，等对方」，与真实状态相反。抢到与没抢到的出参只有 `rewarded` / `credit.delta` 不同，前端一处逻辑即可渲染。

**错误码**：401 未登录 / 400 缺 `relation_id` / 403 非当事人 / 404 关系不存在 / 409 关系非 active。

### 3.3 `report-review`（新建，**仅管理员**）

**入参**：`{ token, report_id, action: 'upheld' | 'dismissed', reason? }`

**出参**：
```json
{ "code": 0, "msg": "ok", "data": { "report_id": "…", "status": "upheld", "credit_delta": -10 } }
```
- 管理员判定同 `verify-review/index.js:93`：`me.is_admin === true || me.role === 'admin'`，否则 **403**。
- `upheld`：`reports.status='upheld'`、`handled_by`/`handled_at` 写全；若 `target_type === 'user'` 则给被举报人 **−10**（`reason_code='report_upheld'`，`ref_id` = report_id）。`target_type` 不是 `user`（卡片/消息/资料）时**不扣分**，`credit_delta` 返回 0。
- `dismissed`：只改状态，不扣分。
- 已经处理过的（`status !== 'pending'`）→ **409**。
- 同一举报不能重复扣分（靠 409 保证）。

### 3.4 `verify-review`（改造，接口不变）

- 出参完全不变，前端不用改。
- 内部把 `index.js:202-215` 那段「直接算 `newCredit` 再 patch `credit_score`/`credit`」改成**调用内联的 credit 核心**：写一行 `credit_events`（`code='verify_pass'`, `delta=+5`, `ref_id`=申请 id），再 patch 分数。
- 加一条**幂等保护**：同一个 `user_id` 已经有 `reason_code='verify_pass'` 的流水时，**不再重复加分**（认证可以重提交，不能重复拿分）。这一点现在没有，是这次要补的。

## 5. 铁律提醒（写代码前必读）

1. `.vue` 模板里**不能**直接用 `<script>` 顶层 `const`，一律挂进 `data()` 或用 `this.`。
2. 云函数业务错误**走 `code` 不走 `throw`**；`catch` 里 `return { code: e.bizCode || 500, msg: e.message }`。
3. 每个云函数目录自包含：只有 `index.js` + `package.json`，**不许 `require` 目录外的东西**。
4. 表不存在时**静默降级不报错**（`try/catch` 兜住查询），但 `uni-id-users` 拿不到用户必须返 500。
5. 改完必须 `node --check`（本机 node 在 `C:\\Users\\lenov\\.dsh\\dsh-runtimes\\dsh-primary-runtime\\dependencies\\node\\bin\\node.exe`，PATH 里没有）。
