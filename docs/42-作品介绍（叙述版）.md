# 同频 · 校园搭子 App　作品介绍

作者：张瑜　　学校：重庆外语外事学院　　指导老师：封明杰

---

## 一、为什么想做

我在学校里反复遇到同一种处境：**这件事我想做，但缺一个人。**

周三下午想去图书馆坐四个小时，一个人容易刷手机；晚上想去操场跑十圈，一个人跑三天就断了；三食堂新开了一家店，一个人去不划算，要凑份量。这些事都不大，也不需要长期伙伴，只需要**此刻有一个人一起**。

它们有三个共同点：**时效短**（就这一个下午）、**半径小**（就在校内或学校周边）、**需要筛选**（得是个靠谱、时间对得上的人）。

而我当时能用的渠道，一个都不合适：

- **群聊**：发一条「有没有人一起去自习」，五分钟就被作业通知和表情包刷过去了，没人接得住；
- **超话、贴吧**：能发出去，但没有任何身份门槛——你不知道对方是哪个学校的、是不是学生，约出来本身就有风险；
- **熟人网络**：最可靠，但也是最贵的一条路——找熟人开一次口，社交成本比自己去还高。

所以问题不是「信息不够多」，而是**没有一个地方，能把「此刻、附近、可信的人」三件事同时凑齐**。同频就是为这件事做的：让校园里那些「就差一个人」的小事，能以最低的社交成本发生。

## 二、我做了一个什么东西

一句话说：**同频是一个用真实校园身份找搭子的应用。它把「想找个人一起做点什么」变成一张结构化的卡片，再按距离与同频程度推给你。**

它由五块能力组成：

**1. 搭子需求卡**
不是一句「有人吗」，而是一张有结构的卡：想做什么（学习、运动、吃饭、玩）、什么时间、在哪、要几个人、自己是什么样的人（作息、强度、性格、兴趣、偏好）。信息填全了，看的人三秒就能判断「这人跟不跟我合」，不用来回问。

**2. 三档同频圈**
校园里的动态按「同校 → 地区 → 发现」三档呈现。同校档最贴，因为它真的只给你本校的人和事；切档不会串数据。这一档不是所有人都能看——**要先通过学生认证**。

**3. 申请、接受、开聊，三步完成匹配**
看到合适的卡点「同频一下」，对方在消息里收到申请，接受之后自动开一个会话。文字、图片都能发，图片不等下载完就先占好位置，翻历史不会被拽回底部。整个过程没有中间的「加好友」环节——校园里的事，快比客气重要。

**4. 学生认证与信誉分**
认证是拿学号和学生证照片人工审的，1 到 2 个工作日。它带来两件事：一是解锁同校频道，二是让别人知道**屏幕对面是个真人、是本校本城的学生**。信誉分记录的是「说好的事有没有做到」，分低了会被限制发布——它不管人品，只管行为。

**5. 大厅与个人中心**
大厅是**所有需求的中心**：不管谁发的、在哪个城市，按「推荐 / 同校 / 附近 / 城市」分档，一律按发布时间往下排。首页则是另一个角色——它只从里面挑**跟你最相关的一小撮**推给你：同校优先，其次附近，再次同城，人少的时候才拿全站补位，并且会明说「这是全站的」。个人中心里，我发过的、我喜欢的、系统推荐的、看过的，都收在一处；再往上是信誉分和称号墙。

形态上，它是**一个安卓 App**；同一套代码也能在支付宝小程序里跑起来。

## 三、我是怎么把它做出来的

**第一步，把问题收敛成一句话。** 我先问自己：如果只能做一件事，做什么？答案是「让人在三十秒内判断出附近有谁可以一起做这件事」。凡是帮不上这个判断的功能，一律不做。这个自我约束救了整个项目——它让我砍掉了本来会拖垮进度的私信、动态广场、积分商城。

**第二步，先定数据与流程，再动画面的。** 一张卡要有哪些字段、认证要走几步、申请到会话中间有几个状态，这些我先在纸上写完，才去画界面。因为流程一旦返工，改的不是一个页面，是整条链路。

**第三步，一个页面一个页面地落地，每做完一个就在真机上跑。** 我不相信「看起来对」，只相信「在手机上点一遍对」。首页的卡片分档、大厅的四档切换、同频圈的三档、聊天的首帧位置，每一条都是真机上反复看出来的问题——比如聊天页原来每次进会话都会先跳到最上面再弹回底部，用户看到的就是闪一下；后来改成「先藏住、等布局算完、再一次性放出来」，这个闪才没了。

**第四步，把「不体面」的细节一个个修掉。** 头像加载不出来时，早期版本会显示一个默认灰头像，等于告诉用户「这个人没头像」；现在改成**宁可空着，也不放默认图**——图没到就是空圆，图到了淡入。图片、头像这类东西，做成「先落盘、下次直接用」，第二次进来就不会白一下。这些细节没人会夸，但缺了就会被说「像半成品」。

**第五步，找出错，而不是猜出错。** 有一个很典型的例子：我自己登录时能看到某个同学的头像，换一个账号登录，同一张卡上就变成空圆。一开始以为是网络或权限，后来顺着「同一个文件为什么这台设备有、那台没有」查下去，才发现是**读取头像时优先取了一个可能已经过期的临时地址**——有本地缓存的设备还能显示，没有的就只能是空的。改成「先取永久标识、取不到再退而求其次」，问题才真正消失。这类问题我后来定了一条规矩：**先找到根因，再动手改**，不先试三个方案碰运气。

**第六步，把验收清单写下来。** 每改一处，我都列清楚「要在这几个页面上看什么」。改动越多，越容易改好一个、碰坏另一个——比如有一次清理临时调试代码，连带删掉了首页滚动时的收纳效果，是照着清单一眼看出来的。

**关于 AI 的参与，我想说清楚分工。** 这个项目的定位、取舍和真机验收是我做的：哪些功能不做、认证为什么是同校频道的开关、大厅和首页各自该扮演什么角色，这些判断错一次就要返工一周。而定位问题的根因、写具体的修改、写自检和文档，我大量交给了 AI——包括上面那个「过期临时地址」的排查，是它顺着证据链找到的。我的体会是：**AI 写代码很快，但它不知道你要什么；人知道要什么，但一个人做不完。** 我用在后者上的时间，比前者多。

## 四、视频里能看到什么

这支视频是拿真机录的，没有剪辑特效，按用户实际会走的路走一遍：

**开头**是启动到首页。第一屏就能看到头图、一叠搭子卡片，和两个数字——我的需求、我的搭子。右上角是每条卡片的归属：同校、附近、城市，人少的时候会是**全站**。

**接着是登录**。这个应用的未登录状态不是一堵墙：不登录也能逛大厅、看卡片，只有要发需求、要申请的时候才要求身份。

**然后是首页的卡片**。点开一条能看到完整需求，上滑卡片堆会展开成列表，档位标签和信誉分都在卡上——先看「跟我合不合」，再看「这人靠不靠谱」。

**接着进学生认证**。展开学校选择、上传学生证，页面底部有一行小字：转校了可以在这里重新认证。认证通过之后，同校那一档才真正打开。

**再往后是同频圈**。依次点同校、地区、发现，三档内容各自独立——切档不会把别的档的数据带过来。

**发布需求**那段，是把「想做什么、什么时候、在哪、几个人、我是什么样的人」一项项填进去，发布后这条卡就出现在首页顶部和大厅里。

**匹配**是全片最想让人看的一段：打开别人的卡片点「同频一下」，切到消息，对方收到申请，接受，会话直接开好——申请、接受、开聊，三步，没有加好友这一步。

**会话里**发一条文字、再发一张图。图片不会先挤成一个小方块再撑开，位置一开始就是对的；往上翻历史也不会被拽回底部。

**我的页**是收口：我的搭子、我喜欢、推荐、观看历史都在这里，再往上是信誉分和已经拿到的称号。

**最后一段**切到后台审核：一条待审记录展开，看到的是认证信息与「旧学校 → 新学校」的换校申请，点通过之后对方才生效。也就是说，认证不是自动放行的，是有人真的在看。

**结尾**回到首页，画面停在那句「同频」上。

## 五、我知道它还不够的地方

- **数据规模小**：现在库里的需求和动态是演示数据，真实校园的量级没验证过；
- **审核靠人**：认证和内容都是人工看，人一多就是瓶颈，这条迟早要半自动化；
- **信誉分偏简单**：目前只记录「说好的事有没有做到」，还没覆盖爽约、放鸽子之外的复杂情形；
- **下一步想做的一件事**：让用户用一句话说需求（「周三下午想去图书馆自习，想找人一起」），由助手把卡片预填好，用户确认后发布——把「填六个字段」变成「说一句话」。这件事我评估过工作量，不重，但它会把发布门槛再降一档。

以上，就是这个作品从念头到成品的全过程。
