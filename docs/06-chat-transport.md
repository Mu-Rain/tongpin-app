# 06 · 聊天传输层设计（MVP 轮询 → 将来可替换为 WebSocket）

> v0.2（2026-10-16）：新建。技术栈 uni-app + uniCloud；MVP 用「消息表 + 3 秒轮询」，预留「换传输层」的接口。
> 配套文档：[02-pages-and-flows.md](./02-pages-and-flows.md) §3.3 · [03-database.md](./03-database.md) §2.4/§3.5 · [04-tech-stack.md](./04-tech-stack.md) §2.1
> 对应代码文件：**`dazi-app/app/common/chat/transport.js`**（也就是说：这一章描述的东西，最终只落在这一个文件里）

---

## 1. 为什么要留这个接口（先讲动机，再讲代码）

**直接原因**：33 天、一个人、代码全靠 AI。实时聊天（WebSocket）要自己起服务、做心跳、做重连、做鉴权，任何一项出问题都会拖垮主链；而 **3 秒轮询只需要一张消息表和两个云函数**，第一天就能跑通。**先把"能聊天"这件事做完，再谈"多快"。**

**为什么不能"先用轮询凑合、以后推倒重写"**：如果页面里到处都是 `setInterval` + `uniCloud.callFunction`，将来换 WebSocket 就得改聊天页、会话列表页、可能还有消息页的红点逻辑——**页面一改就有回归 bug**，而你只有 33 天。

**所以定了这条规则**：

> **页面只调用 `createChatTransport()` 返回的对象，永远不直接调云函数、永远不自己写定时器。**

这样"轮询"就只是一份**实现**（一个可替换的插槽）。将来要换 WebSocket，**只新增一个实现文件、改工厂函数里的一行返回**，页面和数据层一个字都不用动。

```
聊天页 (pages/chat/chat.vue)
   │  只认识 7 个接口：start / stop / send / fetchSince / onMessages / onStatus / onError
   ▼
createChatTransport()  ← 工厂函数：想换传输方式，只改这里
   ├── pollingTransport.js   ← MVP：3 秒轮询（现在用这个）
   └── wsTransport.js        ← P1：WebSocket（将来新增，其它文件不动）
```

## 2. 接口（页面唯一的合同）

`createChatTransport(options)` 返回一个对象，页面只依赖下面这些：

| 成员 | 签名 | 作用 |
|---|---|---|
| `start()` | `start(): void` | 开始接收消息。**进聊天页时调**。轮询实现里会"立即拉一次 + 启动定时器" |
| `stop()` | `stop(): void` | 停止接收、清理定时器。**离开页面（onUnload）/ 退到后台时调** |
| `send(payload)` | `send({ type, content, clientMsgId }): Promise<消息>` | 发送一条消息。返回**服务端消息对象**（带 `_id`、服务端 `created_at`） |
| `fetchSince(lastMessageId)` | `fetchSince(lastMessageId): Promise<消息[]>` | 拉取比 `lastMessageId` 新的消息。断线重连补拉、首次加载都用它 |
| `onMessages(cb)` | `onMessages(cb: (messages: 消息[]) => void): void` | 有新消息时回调（增量数组，可能多条） |
| `onStatus(cb)` | `onStatus(cb: (status) => void): void` | 连接状态变化回调：`connecting` / `online` / `offline` |
| `onError(cb)` | `onError(cb: (err) => void): void` | 出错回调（网络失败、云函数报错） |

**入参 `options`**：

| 字段 | 说明 |
|---|---|
| `conversationId` | 哪个会话 |
| `lastMessageId` | 起点。首次加载传空，断线重连传本地最后一条的 `_id` |
| `onMessages` / `onStatus` / `onError` | 三个回调（也可以事后用 `onXxx()` 注册） |
| `pollInterval`（仅轮询实现用） | 轮询间隔，默认 3000ms |
| `idlePollInterval`（仅轮询实现用） | 静默时的间隔，默认 10000ms |

> 页面拿到消息后，**只做一件事**：把消息合并进本地列表（按 `clientMsgId` / `_id` 去重），然后更新未读数。它不知道消息是"推"来的还是"轮"来的。

## 3. 轮询实现的 6 个要点（每一条都是踩过坑才总结出来的）

### 3.1 进页面立即拉一次

`start()` 里**先立刻 `fetchSince(lastMessageId)`，再启动定时器**。不要只启动定时器（那样最坏要等 3 秒才看到消息，体验差，还会让用户以为卡了）。

### 3.2 活跃 3 秒，静默 3 分钟后降到 10 秒

| 状态 | 间隔 | 为什么 |
|---|---|---|
| 活跃（用户刚发过消息 / 刚收到消息 / 正在输入） | **3000ms** | 聊天时体验优先，3 秒是"几乎感觉不到延迟"和"调用量可接受"的平衡点 |
| 静默（连续 3 分钟没有任何收发、没有交互） | **10000ms** | 人已经不看了，没必要每 3 秒问一次服务器。**这是省免费额度的主要手段** |

判断"活跃"用两个信号：最近一次收发消息的时间、最近一次页面交互（输入框 `@input`、滚动）。恢复活跃就立刻回到 3 秒，并**马上补拉一次**（静默期间可能已经攒了好几条）。

### 3.3 离开页面立即停止

在页面 `onUnload`（以及 App 退到后台时）调 `stop()`：**清掉定时器、把在途请求标记为作废**。

> 为什么不"在后台继续轮询"：① 白白消耗你的云函数免费额度；② 手机耗电，用户会骂；③ 后台消息提醒已经交给 uni-push 了（见 §3.7），职责不要重复。

### 3.4 请求不并发重叠（这条最重要，最容易写错）

**必须保证同一时刻只有一个在途请求。** 具体做法：一个 `isFetching` 标志位，`true` 时定时器这轮**直接跳过**，不发起新请求；请求回来（无论成功失败）在 `finally` 里把它置回 `false`。

> 为什么：如果网络慢（2G / 校园网抖动），3 秒的定时器会不断堆积请求，导致 ① 响应乱序、旧数据覆盖新数据；② 云函数调用量翻好几倍，**免费额度可能被瞬间打爆**；③ 页面消息重复或跳动。
> 这条是轮询方案的生命线，**代码 review 时第一眼看它**。

### 3.5 消息去重（`clientMsgId` + `_id`）

发送侧和接收侧都要去重，因为**重复是常态**（网络重试、用户连点、断线补拉重叠）。

| 场景 | 去重依据 | 做法 |
|---|---|---|
| 自己发的消息 | `clientMsgId` | 点发送时**先在本地插一条"发送中"气泡**（`clientMsgId` 本地生成，如 `时间戳+随机串`）。云函数按同一个 `clientMsgId` 判重：已存在就返回老那条，不重复写入。返回后用 `clientMsgId` 找到本地气泡，状态改成"已送达"，并补上服务端 `_id` |
| 拉回来的消息 | `_id` | 合并前查本地列表有没有这个 `_id`，有就跳过 |

> 效果：**发送失败可以放心重发**（重发带同一个 `clientMsgId`，服务端不会存两条），用户在列表里也不会看到两条一样的消息。这正是 US-19 验收标准里"断线自动重连并补拉未收到的消息 / 发送失败可重发"的实现方式。

### 3.6 断线补拉（`lastMessageId`）

每次成功收到消息后，把**最新一条的 `_id` 存进内存（并写进本地缓存）**，作为下一次 `fetchSince` 的参数。

- 网络错误 / 云函数报错时：状态置 `offline`，**保留 `lastMessageId` 不推进**，退避重试（如 3s → 6s → 12s，最多 30s）；恢复后一次补拉就能拿到全部漏掉的消息。
- 重新进页面时：从本地缓存的 `lastMessageId` 开始拉，**不会丢掉关页面期间收到的消息**。

> 实现提示：`_id` 是自动生成的字符串，**不保证严格递增**。所以云函数里 `fetchSince` 的正确写法是「按 `created_at` 过滤并排序，用 `_id` 去重」，不要只靠 `_id > xxx` 大小比较。这一点在 [03-database.md §3.5](./03-database.md) 里也写了。

### 3.7 离线提醒靠 uni-push

App 不在前台 / 锁屏时**没有轮询**（定时器会停），所以：

- 服务端写消息的云函数里，给**对方**发一条 uni-push 通知："你有一条新消息"。
- 通知**只做提醒，不带内容**（隐私：锁屏上不该出现聊天内容）。
- 点通知打开 App → 进聊天页 → `start()` 里立即补拉 → 消息就齐了。

> uni-push 是"最终会到"，不是"实时"。**不承诺秒到**，答辩时就这么说，别给自己挖坑。

### 3.8 未读数策略

| 场景 | 做法 |
|---|---|
| 收到新消息、且**当前不在这个会话页** | `conversation_members.unread_count + 1`（在写消息的云函数里顺手做，一次请求搞定） |
| 进入会话 | 记录 `last_read_message_id = 最新消息 _id`，并把 `unread_count` 置 0 |
| 正在会话页时收到消息 | 直接置 0（用户正在看，不该出现红点） |

> 未读数放 `conversation_members` 而不是每次去 `messages` 数——**数消息是要遍历的，几十个会话列表会卡**。用 `(user_id, unread_count)` 索引，消息页红点一次查询就能拿到。

## 4. 换 WebSocket 时要改什么（这就是留接口的价值）

**要改的（两个地方，都是新增，不是重写）：**

1. **新增一个文件** `dazi-app/app/common/chat/wsTransport.js`，实现同样的 7 个接口（`start` / `stop` / `send` / `fetchSince` / `onMessages` / `onStatus` / `onError`）。
2. **改工厂函数的一行返回**：`createChatTransport()` 里根据配置（或按会话类型）返回 `wsTransport` 而不是 `pollingTransport`。

**不改的（这是重点）：**

- 聊天页 `chat.vue` —— 它只认识那 7 个接口，**一个字都不用改**；
- 会话列表页、消息页红点逻辑 —— 不依赖传输方式；
- 数据层与集合设计（`messages` / `conversations` / `conversation_members`）—— WebSocket 传的**还是同一条消息**，只是"怎么送到客户端"变了；
- 云函数 `message-send` —— 照旧负责落库、去重、更新未读数。**"消息表"始终是真相来源，WebSocket 只是加速的部分。**

**但要注意：换 WebSocket ≠ 只是换个函数。** 自建 ws 服务要多操这些心：

| 要操心的 | 具体是什么 |
|---|---|
| **要一台服务器** | uniCloud 云函数**不支持常驻 WebSocket 连接**，所以换 WebSocket 意味着你要自己租服务器、部署 ws 服务（这就是原来那套自建后端的代价） |
| **鉴权** | 客户端连上时怎么证明"他是这个会话的成员"（连接时带 token，服务端校验） |
| **心跳** | 定期 ping/pong，否则中间网络设备会静默断开连接，用户以为"对方不理我" |
| **重连** | 断线自动重连 + 指数退避 + **重连后补拉**（这一步和轮询完全一样，`fetchSince` 复用） |
| **消息必达** | 连接不可靠：发送要带 ack，没收到 ack 就重发（靠 `clientMsgId` 去重，逻辑也已经有了） |
| **在线状态** | 顺便可以做"对方在线"，但这是新功能，要新字段、新页面表现 |
| **灰度** | 不要一次全量切。**先用"新会话用 ws、老会话用轮询"或"设置里手动切换"跑一周**，确认稳定再全换 |

**什么时候才值得换（P1 的触发条件）：**

- 用户反馈"消息到得慢"成为主要投诉；或
- 同时在线的内测用户明显变多，3 秒轮询的云函数调用量开始逼近免费额度；或
- 你想做"正在输入""已读回执"这类只有在长连接上才自然的功能。

> 在那之前，**别碰它**。33 天里，主链能演示 > 传输层先进。

## 5. 自查清单（写 / 改聊天相关代码时逐条过）

| 检查项 | 通过标准 |
|---|---|
| 页面里有没有 `setInterval` 或直接 `uniCloud.callFunction`？ | **必须没有**。页面只能调 transport 的 7 个接口 |
| `stop()` 有没有在 `onUnload` 里调？ | 有，否则离开页面还在轮询，白烧额度 |
| 在途请求会不会重叠？ | 有 `isFetching` 标志位，`finally` 里复位 |
| 发送会不会产生两条？ | 有 `clientMsgId`，云函数按它判重 |
| 拉回来的消息会不会重复渲染？ | 合并前用 `_id` 去重 |
| 断网恢复后会不会丢消息？ | 保留 `lastMessageId`，恢复后 `fetchSince` 一次补齐 |
| 时间用的是服务端时间吗？ | `messages.created_at` 由云函数用 `Date.now()` 写入 |
| 消息是不是只有会话成员能读？ | `messages` 的 `client` 为 `false`，四个权限全 `false`，**只能通过云函数读**，云函数里校验成员身份 |
| 锁屏时对方能收到提醒吗？ | 写消息的云函数里给对方发 uni-push（不带消息内容） |
| 正在会话页收到消息，红点会不会闪？ | 直接置未读 0 |
